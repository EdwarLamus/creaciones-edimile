05 · Decisión técnica clave

SQL vs. NoSQL

¿Por qué cambiamos de MySQL a Firebase Firestore?

05

MySQL (propuesta inicial) vs. Firebase Firestore (implementado)

🗄 MySQL · Relacional (SQL) Criterio 🔥 Firebase Firestore · NoSQL
Requiere servidor propio (o VM). Costo fijo mensual aunque no haya tráfico. Infraestructura Serverless. Se paga solo por lecturas/escrituras reales. Escala a cero. ✔ Firestore
JOINs complejos para cargar una cotización: cotizaciones + items_cotizacion + clientes + usuarios (4 tablas). Consultas Cotización guardada como documento con ítems embebidos. Una sola lectura, sin JOINs. ✔ Firestore
Si el cliente cambia su nombre, todas las cotizaciones antiguas reflejan el nombre nuevo (inconsistencia histórica). Integridad histórica Datos del cliente desnormalizados en cada cotización/venta. Snapshot inmutable. ✔ Firestore
Agregar un campo requiere ALTER TABLE + migración en producción. Riesgo de downtime. Flexibilidad de esquema Schema-less. Se añaden campos sin migraciones ni downtime. Ideal para evolución ágil. ✔ Firestore
Requiere configuración manual de backups, SSL, usuarios de DB, firewall, etc. Mantenimiento Google gestiona backups, replicación, seguridad y alta disponibilidad automáticamente. ✔ Firestore
Relaciones muy complejas y reportes con GROUP BY / SUM avanzados son más naturales. Queries analíticos Requiere diseño cuidadoso. Se resuelve con agregaciones en el servicio Java. Empate

Patrón Snapshot — la clave del diseño NoSQL

❌ Problema con SQL normalizado

La cotización tiene cliente_id = 5.
Si el cliente cambia su nombre de "Carlos Ruiz" a "Carlos Ruiz Hernández",
todas las cotizaciones históricas mostrarán el nombre nuevo.
Los documentos ya entregados ya no coinciden con el sistema.

✔ Solución con patrón Snapshot (Firestore)

Cuando se crea la cotización, se copia el nombre, documento y datos del cliente dentro del documento de la cotización.

Si el cliente cambia sus datos, las cotizaciones/ventas históricas conservan los datos tal como estaban en el momento de la transacción.

📊 Comparación de consultas

SQL — Cargar cotización COT-0001

SELECT c.*, cl.nombre, cl.documento,
       u.nombre as vendedor,
       ic.descripcion, ic.cantidad, ic.precio
FROM cotizaciones c
JOIN clientes cl ON c.cliente_id = cl.id
JOIN usuarios u  ON c.usuario_id = u.id
JOIN items_cotizacion ic ON ic.cotizacion_id = c.id
WHERE c.numero = 'COT-0001';

4 tablas · 3 JOINs · múltiples round-trips

Firestore — Cargar cotización COT-0001

db.collection("cotizaciones")
  .whereEqualTo("numero", "COT-0001")
  .get();

1 colección · 0 JOINs · 1 lectura · datos completos

Seguridad del Sistema

🔐

Contraseñas con BCrypt

Ninguna contraseña se almacena en texto plano. Spring Security aplica hashing BCrypt con salt automático.

🛡

Control de roles

Cada URL y método del sistema está protegido con @PreAuthorize. El acceso se verifica en cada petición.

🔒

HTTPS obligatorio

Firebase Hosting y Cloud Run sirven todo el tráfico por HTTPS. Certificados gestionados por Google automáticamente.

✉

Tokens de recuperación

Los tokens de restablecimiento de contraseña son UUID únicos con vigencia de 1 hora y uso único.

🕐

Sesiones con expiración

Las sesiones expiran automáticamente tras inactividad. Spring Security invalida la sesión al cerrar sesión.

🔥

Reglas Firestore

Firebase Firestore solo acepta peticiones autenticadas desde el servidor backend. No hay acceso directo desde el navegador.
